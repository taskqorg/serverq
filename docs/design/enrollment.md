# Independent DashQ connection

Accepted implementation target under [serverq.md](../../serverq.md). Apply [shared connection semantics](https://github.com/taskqorg/specq/blob/main/engineering/product-connections.md) through the coreq linked client and [DashQ C1–C7](https://github.com/taskqorg/dashq/blob/main/docs/design/enrollment.md). Implemented as `serverq enroll`, `connection status` and `disconnect` ([serverq.md § 2, § 5](../../serverq.md#5-service)); qualified below.

`serverq enroll <https-url>`, `serverq connection status` and `serverq disconnect` use the same browser/headless approval, protected credential, projection receipt and revoke lifecycle as AgentQ. No AgentQ installation or Langfuse dependency. The existing service handles delivery; no extra daemon or scheduler. Stable random installation identity survives updates, never derives from hostname; lost identity creates a new installation.

Send only a coalesced latest unsent snapshot. Connection state and credentials are durable and excluded from pruning; they contain no authoritative product state. Heartbeat freshness and underlying observation freshness remain separate. Snapshot transport failure never changes primary command success or blocks primary work. C3's accepted credential lifetime exception is confined to observation, never commands or forge access.

## ServerQ projection

Existing checks, report/state formats and rules.json remain authoritative. Produce an allowlisted projection: installation/runtime/version, catalog hash, per-rule ID/status/original observation time/reason, numeric evidence and incident verification state. Manual rules stay unverified; unsupported probes stay unknown. Retain schema-1 readers through additive metadata only. Never export raw detail, paths, unit names, container IDs or report.json wholesale; use fixed-vocabulary reasons. Recommendations reference the exact rule/catalog revision, never duplicate thresholds. Implemented as `serverq projection` (fields and reason vocabulary: [serverq.md § 3](../../serverq.md#3-check-and-report)); delivered through coreq after each check.

A fresh connection may expose an old report as stale; it cannot rerun or repair checks remotely. No implied cross-product host/filesystem join. Historical findings research supplies context, not additional approved features.

## Qualification

Prove an independently installed product can enroll, show a real matching snapshot in DashQ, recover after network/store restart, disconnect offline, revoke and reconnect without identity or scope leakage. Test denied/wrong-workspace requests, lost replies, bounded storage, schema compatibility and primary-function independence. Reuse coreq conformance; do not reimplement its auth or transport. Ship only after applicable E1–E10 and the product's normal checks pass.

### Evidence (coreq v0.11.0, DashQ v0.9.0 and v0.9.1)

Live against `https://dash.ufobe.com/machine`, workspace `gradus`, no AgentQ or Langfuse on the hosts. Each run printed one pairing code; after one owner approval `enroll --headless` printed `Connected ... generation 1 snapshot r-...` (receipt `projected`) and `connection status` exited 0 with that snapshot `projected`.

- macOS aarch64, 2026-10-15, 3a66168: then `disconnect` printed `Disconnected` (revoked, exit 0) and `connection status` read `disconnected`, exit 2.
- WSL Ubuntu 24.04 x86_64 and native Windows 11 x86_64, same host label `DESKTOP`, 2026-10-15, binaries built from 145c23e (`src/` as 3a66168): two installations, `14baeb23...` and `79f3ceb9...`, each its own grant. Projection: WSL 3 `ok`, 1 `warn`, 1 `unknown`; Windows 5 `unknown` (`unsupported-os`); 4 manual rules each.
- Service recovery, same two installs, live delivery: WSL as a systemd user unit with `Restart=always` (`systemd-run`), `kill -9` of its main process, systemd restarted it (`NRestarts` 1) and the next check's snapshot was `accepted` then `projected`; Windows under the coreq launcher, the `service run` child killed, the launcher restarted it after 60 s and delivery resumed. Both kept grant generation 1: no new pairing.
- E1 page match, DashQ v0.9.1, read on the FRA loopback (`/data` and `/`), 2026-10-15: both installations listed under workspace `gradus`, generation 1, `active`, schema `serverq-report/1`, each with its own installation ID. The page and `/data` agree rule for rule with the projection: WSL 4 `ok` and `bounded-journal` `warn` (`missing-journal-bounds`, one observed incident); Windows 5 `unknown` (`unsupported-os`); 4 manual rules `not verified` each. WSL `bounded-docker-logs` reads `ok` because that distribution has neither a Docker CLI nor `/var/run/docker.sock` (specified "System Docker not installed"). The earlier `unknown` from the enroll run is not reproduced and its reason was not recorded; `unknown` there means a socket without a CLI or a failed collection. Reports 1792003749/1792003753 were followed by 1792007349/1792007353, exactly the hourly check interval: delivery continues, a report 20 min old is not a stopped client. The 1792007349 WSL report reads all 5 `ok` (journal bounds present then); the page follows the latest report.
- Non-WSL Linux server, FRA (`hermes-fra1`, Ubuntu 24.04.4 x86_64), 2026-10-15, static musl binary built from the d0d646c tree, in a separate `--home` beside the production 1.0.0 install, which stayed untouched: `selftest` passed, `check` exit 0 (5 `ok`), one owner approval, `enroll --headless` `Connected` generation 1, receipt `projected`. Connection folder 0700, `connection.json`, `sent.json` and `lock` 0600. The service ran as a transient user unit `serverq-qual` (`systemd-run`) with the § 5 unit's properties (`Restart=always`, `RestartSec=10`, `UMask=0077`, sandbox, caps), checks every 60 s and updates off; `service install` was not used because it writes the production host's `serverq.service`. Its first check's snapshot was `projected`; `kill -9` of the main process, systemd restarted it (`NRestarts` 1), the next check's snapshot was `projected`, same generation, no new pairing. DashQ `/data` (FRA loopback) listed installation `087b6b23...`, host `hermes-fra1`, `active`, 5 `ok` and 4 manual, matching the projection. Then `disconnect` exit 0, `connection status` `disconnected` exit 2, DashQ `revoked`; the unit and the test install were removed.
